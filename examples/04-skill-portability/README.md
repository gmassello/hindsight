# Scenario 04 — Skill portability

**The question this run answers: does [`skills/datahub-incident-triage/`](../../skills/datahub-incident-triage/) actually work on its own, or is it a text file nobody ever executed?**

The open source Skill is Hindsight's procedure distilled into instructions — no orchestrator, no
Python, no scoring code. The claim it makes is that any Agent Skills-compatible CLI with DataHub
connected reproduces the agent's behaviour without this repository. This run tests that claim.

## Setup

An agent was given the same incident text as [`01-schema-drift`](../01-schema-drift/), told to
follow `SKILL.md` and nothing else, and connected to `mcp-server-datahub` against the local
DataHub quickstart. **No Hindsight backend code was in the loop** — not the orchestrator, not the
phase prompts, not `datahub/lineage.py`. The impact scores below were computed by hand from the
formula in the skill's own `references/impact-scoring-reference.md`.

## Result

| Measure                           | [`01-schema-drift`](../01-schema-drift/) (Hindsight) | This run (Skill only)           |
| --------------------------------- | ---------------------------------------------------- | ------------------------------- |
| Resolved asset                    | Snowflake `orders`                                   | Snowflake `orders` — same URN   |
| Prior incidents recalled          | 1                                                    | 4                               |
| Investigation tool calls          | 16                                                   | **9**                           |
| Consumers found                   | 20                                                   | 30                              |
| Owners to notify                  | 14                                                   | **the same 14**                 |
| Top root cause                    | upstream Postgres incident, 90%                      | schema drift upstream, 90%      |
| Second hypothesis                 | — (single hypothesis)                                | upstream Postgres incident, 75% |
| Mutations applied                 | 3                                                    | 3 + postmortem                  |
| Postmortem retrievable afterwards | yes                                                  | yes — second hit on re-search   |

The second hypothesis is verbatim what `01-schema-drift` concluded, on the same evidence. The first
is something the Hindsight run never reported: the
`ALTER TABLE order_entry.orders ALTER COLUMN customer_id DROP NOT NULL;` note on the asset itself —
precisely what `scenarios/break_schema.py` plants as the scenario's actual cause, where
`01-schema-drift`'s postmortem cites only the upstream tag.

## Caveats

- **9 calls versus 16 does not mean the skill beats Hindsight.** This run found **4** prior
  postmortems in memory; `01-schema-drift` found **1**. Much of the difference is accumulated
  memory. The defensible claim is convergence, not a speed record.
- **Warm run.** The Postgres ancestor was already tagged `hindsight-degraded` by earlier runs,
  which is what made `upstream_incident` cheap to confirm. The memory loop working as designed,
  but not a cold start.
- **`audit-log.json` was captured by hand** from the MCP responses, not generated by
  `cli.py:_write_report`. Same schema so the files read side by side, minus `timestamp` (omitted
  rather than fabricated) and plus `response` (the server's reply); the postmortem body lives in
  `postmortem.md` instead of inlined into the `save_document` args.
- **`postmortem.md` is verbatim, including its defects** — see below.

## What the run found in the skill

The verification was not a formality. Three real defects, all since fixed:

1. **`grep_documents` requires a `urns` argument.** It narrows an existing result set; it does not
   search the catalog. Step 3 told the agent to look up an asset name and URN with it directly,
   which fails outright. It now runs over the URNs `search_documents` returned.
2. **`get_lineage_paths_between` takes `source_urn` / `target_urn`**, not
   `upstream_urn` / `downstream_urn`. The agent guessed and burned a turn. The real signatures are
   now inline in Step 5, where they are used, instead of buried at the end of the file.
3. **The skill let the agent summarise the postmortem.** Compare `postmortem.md` against
   `blast-radius.md`: it reports "30 affected consumers within 3 hops" where the server actually
   returned consumers 4 and 5 hops out, lists 5 of the 30 rows, and writes "14 owners across
   ORG_DATA_PLATFORM, ORG_BACKEND_ENG and 12 individual users" where the template asks for the
   URNs. Since `grep_documents` matches literal text, a prose summary is a document the next
   investigation cannot use — the skill was undermining its own memory loop. Step 7 now requires
   every row, every owner URN, and the largest hop count actually observed.

The postmortem was deliberately left as saved: it is what the run produced, and the third defect is
only visible because of it.

## Reproducing it

Bring up DataHub (`colima start && datahub docker quickstart && datahub datapack load showcase-ecommerce`),
plant the scenario with `backend/.venv/bin/python scenarios/break_schema.py`, point any
Agent Skills-compatible CLI at `skills/datahub-incident-triage/` with the DataHub MCP server
configured, and paste `input.txt`. Mutation tools need `TOOLS_IS_MUTATION_ENABLED=true`.

Numbers will differ — memory grows with every run, which is the entire point — but the resolved
asset, the root cause and the owner list should not.
